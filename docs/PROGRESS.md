### Lanjutan (2026-08-26, sesi sama) — dashboard asli, izin/sakit, task (yang paling mudah dulu)
Diminta pemilik project untuk lanjut bertahap, dimulai dari yang paling mudah. Dikerjakan berurutan, masing-masing diverifikasi hidup di container (termasuk lewat browser) sebelum lanjut ke berikutnya.

- **Perbaikan kontrak API sebelum lanjut ke frontend**: ditemukan bahwa `internal/domain/models.go` tidak punya `json` tag sama sekali, sehingga API membalas JSON PascalCase (`{"ID":1,"WorkDate":...}`), bukan snake_case seperti yang didokumentasikan di `docs/openapi.yaml` (`{"id":1,"work_date":...}`). Ini ditemukan saat mau konsumsi `/attendance/today` dari frontend — diperbaiki langsung (menambahkan `json:"..."` tag ke seluruh struct domain yang diserialisasi handler: `Attendance`, `LeaveRequest`, `Task`, `Shift`, `OfficeLocation`, `FieldAssignment`, `User`, `Employee`, dst.) alih-alih membiarkan frontend menyesuaikan diri ke kontrak yang salah. `PasswordHash` juga diberi `json:"-"` (sebelumnya tidak pernah accidentally ter-expose karena handler auth pakai response struct terpisah, tapi tetap perbaikan yang benar untuk struct yang sama sekali belum punya tag apapun). Build/vet tetap bersih, `air` auto-rebuild dan diverifikasi ulang lewat curl.
- **`lib/authedApi.ts`**: helper generik untuk memanggil API Go dengan Authorization header dari cookie httpOnly milik karyawan/admin. Dipakai dua cara: langsung dari Server Component untuk data read-only saat page load (tanpa round-trip lewat Route Handler), dan dari Route Handler untuk proxy submit form dari client component (yang tidak bisa baca cookie httpOnly sendiri).
- **`lib/types.ts`**: tipe TypeScript untuk `Attendance`/`LeaveRequest`/`Task` mengikuti `docs/openapi.yaml`. Belum jadi `packages/contracts` bersama (masih ditunda sampai ada kebutuhan berbagi ke mobile).
- **`/dashboard`**: sekarang menampilkan status presensi hari ini yang sesungguhnya (`GET /attendance/today`) — jam masuk/keluar, flag terlambat/pulang cepat, status, mode WFH/Kantor — menggantikan placeholder klaim JWT.
- **`/leave`**: daftar riwayat pengajuan izin/sakit milik sendiri + form pengajuan baru (gabungan izin/sakit sesuai D-16, status awal "Menunggu" sesuai D-15). Submit lewat `app/api/leave-requests/route.ts` (proxy ber-autentikasi).
- **`/tasks`**: daftar task milik sendiri + form tambah task baru. Submit lewat `app/api/tasks/route.ts`. Catatan teknis: `<input type="datetime-local">` mengembalikan string tanpa timezone (tidak valid RFC3339) sehingga dikonversi ke ISO string penuh di klien sebelum dikirim ke API Go (yang men-decode ke `time.Time`).

- **Diverifikasi hidup lewat browser sungguhan**: dashboard menampilkan data check-in/checkout asli dari pengujian sebelumnya; form izin/sakit berhasil submit dan riwayat langsung ter-render ("Izin, 27 Agu 2026 – 28 Agu 2026, Menunggu"); form task berhasil submit dan task langsung muncul di daftar ("Rekap laporan mingguan", status "planned"). ### Lanjutan (2026-08-26, sesi baru — re-orientasi) — revocation refresh-token saat logout
Menutup simplifikasi yang sudah ditandai eksplisit sejak Phase 2 (bukan bug baru ditemukan) — lihat D-24 di `docs/DECISIONS.md` untuk detail keputusan.

- **Backend**: migration `000012_create_revoked_refresh_tokens` (tabel denylist `jti`+`expires_at`). `authtoken.Issuer.Generate` sekarang menyertakan klaim `jti` (random 16-byte hex, `crypto/rand`) di setiap token yang diterbitkan. `internal/repo/revoked_token_repo.go` (baru): `Revoke` (idempotent, `ON CONFLICT DO NOTHING`) dan `IsRevoked`. `auth.Service.Refresh` sekarang menolak token yang `jti`-nya sudah direvoke; `auth.Service.Logout` (baru) men-decode token yang dikirim dan mencatat `jti`-nya — mengembalikan `nil` (bukan error) untuk token yang gagal di-parse, supaya logout tidak pernah gagal untuk klien yang sesinya sudah invalid/hilang. `AuthHandler.Logout` sekarang membaca body opsional `{refresh_token}` alih-alih no-op murni.
- **Frontend**: `app/api/auth/logout/route.ts` sekarang membaca cookie refresh token milik audiens yang logout (`emp_refresh_token`/`adm_refresh_token`) dan memanggil `POST /api/v1/auth/logout` di API Go **sebelum** menghapus cookie — best-effort (kalau panggilan API gagal, cookie tetap dihapus, supaya klien tidak pernah macet tidak bisa logout secara lokal).
- **Diverifikasi via curl**: dua login independen (dua `jti` berbeda) → logout salah satu → `refresh` sesi itu ditolak (`401`), sesi lain **tidak terpengaruh** (bukti tidak over-broad, tidak accidentally merevoke seluruh sesi employee yang sama). Logout dua kali dengan token yang sama tetap `204` (idempotent). Logout dengan body kosong/tanpa token tetap `204`.
- **Diverifikasi hidup lewat browser sungguhan**: login admin baru di `/admin/login` (supaya refresh token yang tersimpan di cookie sudah membawa `jti` — sesi admin lama dari sebelum perubahan ini tidak punya `jti`, lihat catatan di bawah), klik "Logout" → redirect ke `/admin/login` → dicek langsung ke tabel `revoked_refresh_tokens` di Postgres, baris baru dengan `jti` non-kosong benar-benar tercatat, cocok dengan log `POST /api/v1/auth/logout` di container `api`.
- **Catatan ditemukan saat verifikasi (bukan bug, artefak transisi kode-hidup)**: sesi admin yang sudah login **sebelum** perubahan ini di-hot-reload sempat menghasilkan satu baris `revoked_refresh_tokens` dengan `jti` **kosong** saat logout — karena refresh token lamanya diterbitkan oleh kode lama yang belum menyertakan klaim `jti`, sehingga ter-decode dengan `jti: ""`. Ini murni artefak lingkungan dev yang sedang hot-reload di tengah pengembangan (setara dengan rolling-deploy window di production nyata), **bukan cacat desain** — token baru yang diterbitkan setelah perubahan ini selalu punya `jti` unik, dan risiko teoretis "satu revoke ber-`jti`-kosong memblokir refresh token lama lain yang juga ber-`jti`-kosong" hanya relevan untuk token yang sudah beredar sebelum deploy kode ini, bukan untuk operasi normal ke depan. Baris uji coba di tabel sudah dibersihkan (`DELETE FROM revoked_refresh_tokens`), bukan data produksi.
- `go build`/`go vet`/`gofmt` bersih; `docs/openapi.yaml` diperbarui (`/auth/logout` sekarang mendokumentasikan body opsional `refresh_token`) dan tervalidasi ulang (pyyaml).

**Diverifikasi hidup di dalam container (bukan cuma build/vet):**
1. `docker compose exec api go run ./cmd/seed` → berhasil, mencetak kredensial dev.
2. Login admin (`POST /auth/admin/login`) → JWT dengan `role: superadmin` di klaim.
3. Login employee (`POST /auth/employee/login`) → JWT.
4. `GET /attendance/today` sebelum check-in → `null` (belum ada data, sesuai desain).
5. `POST /attendance/check-in` (lokasi dalam radius 100m) → sukses, `is_late: true` (karena waktu tes jam 11 siang, lewat ambang 09:15 shift `SH01` — sesuai D-10), file foto tertulis nyata di `services/api/storage/checkin/1/*.png` (terlihat langsung di filesystem host karena bind-mount), baris ter-insert di `attendances` (dikonfirmasi via `psql` di container `postgres`).
6. `GET /attendance/today` setelah check-in → mengembalikan baris yang baru dibuat.
7. `POST /attendance/check-in` lagi (checkout) → `status: closed`, `is_early_leave: true` (checkout sebelum jam 17:00 shift), foto checkout tersimpan terpisah (nama file unik, tidak menimpa foto check-in — D-11).
8. `POST /attendance/check-in` lagi segera setelah checkout → ditolak `409 too soon after previous checkout` (cooldown 5 menit multi-siklus, D-23) — membuktikan guard idempotency jalan.
9. `GET /admin/config/shifts` dan `/admin/config/office-locations` dengan token admin → mengembalikan data yang di-seed, RBAC (`RequireAuth` audience admin) berfungsi.
10. Log container `api` menampilkan `flag-no-checkout job: running every 2m0s, threshold 5m0s` — konfirmasi job D-17 aktif berjalan.

Semua kredensial di atas (`admin`/`password123`, `nik 0001`/`password123`) adalah **data dev/demo di container lokal**, bukan untuk lingkungan manapun yang nyata.
